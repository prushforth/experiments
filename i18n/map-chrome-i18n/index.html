Localization of map UI

Most of the words in a map are not in the page. Zoom buttons, the layer control, three context menus, the opacity slider, the search box, the movement announcements a screen reader reads — all of it is supplied by the implementation, which means translating the page does not translate the map. These variants are all in Ukrainian: the documents say <html lang="uk"> and hand the library a table of strings through <map-options>, the escape hatch for a language a library does not bundle.

The content type decides where the map's content text comes from. Inline, the layer is named by a label attribute the page wrote. Remote, it is named by the <map-title> of the fetched document — the one piece of a map's text a server can negotiate, sitting in the same control as the chrome text it cannot. The root element matters because <map> cannot host a shadow root, so the chrome being translated has to be built somewhere other than where it usually lives.

All three implementations resolve a viewer's language the same way: match the element against :lang() for each language they bundle, and fall back to the page's <map-options> table otherwise. What differs is the bundle. MapML.js and MapML-OpenLayers ship English and French, so lang="uk" falls through to the page. MapML-MapLibre also ships Japanese, Swedish and Ukrainian, so :lang(uk) matches a built-in there and the page's table is never consulted — the same language arriving by a different route, which is worth knowing before concluding that a half-filled table works.
