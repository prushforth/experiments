Localization of map UI, declared inline in a <map is="web-map">

The same Ukrainian chrome, hosted by the customized built-in <map>. Worth its own page because the chrome has to be built somewhere else: a <map> cannot have a shadow root of its own, so the viewer puts its controls on a child element instead. If the buttons, the layer control and the context menus are still in Ukrainian, the locale lookup followed the map rather than the shadow root it usually lives in.

MapML.js (Leaflet)

web-map.js is a near-duplicate of the autonomous viewer upstream, including its own copy of the :lang() lookup — so this frame is a real second implementation of the same rule, not the same code twice.

MapML-MapLibre

Customized built-ins are not implemented in WebKit, so in Safari this frame stays an inert <map>: no map, and no chrome to translate. Everywhere else it resolves Ukrainian from its own bundle, as in the <mapml-viewer> variant.

MapML-OpenLayers

One viewer implementation shared by both root elements, and the locale is resolved from the element the author wrote — which is the <map> here and the <mapml-viewer> next door. Asking the wrong element for :lang() is exactly the bug this page would catch.

:lang() is inherited, so no element here carries a lang attribute of its own: the map is Ukrainian because the document is, which is the behaviour an author would expect from any other localized widget. Put a <map is="web-map" lang="fr"> inside an English page and only that map turns French.

The remote variant moves the layer's name out of the page and into the layer's own document, which is the only part of a map's text a server can negotiate.
