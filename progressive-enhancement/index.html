Progressive enhancement / graceful degradation

A client-side image map that becomes an interactive map: the same <map name="dowslake"> carries <area is="map-area"> hotspots for the <img usemap> beneath it and <map-layer> children for the map that replaces it. With scripting, or in a browser that supports customized built-in elements, you get the map; without either, you get the image and its links.

Variants Inline only <map is="web-map"> only

MapML.js (Leaflet)

The reference implementation: the <map> hosts the map chrome on a child <div class="mapml-web-map">, hides the poster image, and draws each <area> as a vector on top of the layers.

MapML-MapLibre

Same markup, same fallback. The areas are hit-tested by the renderer rather than by the browser's own image map, so an area with no href — the hole in the donut — is inert in every implementation.

MapML-OpenLayers

The <area> element is its own style probe here, so the inline style on each hotspot is resolved by the real CSS cascade, and the alt text becomes the hover title.

There is no <mapml-viewer> variant: progressive enhancement here depends on <map name>, <area> and <img usemap> — markup the browser already understands — and an unknown element cannot be the target of a usemap attribute. There is no remote variant either: what degrades is the markup in the page, and a fetched MapML document is not there to degrade to when scripting is off.

Each framed page carries its own PE/GD stylesheet inline rather than relying on the shared experiment styles, because with scripting off the script that loads those styles never runs.

In WebKit, where customized built-ins are not implemented, the <map> is :defined all the same — it is an ordinary built-in element — so the note under each frame reports support from the host <div class="mapml-web-map"> an upgraded map creates instead, and says plainly that you are looking at the image map rather than a map.
