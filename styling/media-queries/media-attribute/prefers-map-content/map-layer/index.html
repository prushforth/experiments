Choosing a representation by prefers-map-content, with media

The same data — the probability of minimum annual snow and ice over Canada — offered as a WMS image, as tiles, as features, and as a table of descriptions, with the query on each <map-layer media>. Press the preference buttons: nothing in the page touches a layer, and a layer whose query does not match is never fetched.

Mechanism media attribute matchMedia() API
Gated element <map-layer> <map-link>

Variants Remote only <mapml-viewer> only

MapML.js (Leaflet)

The reference implementation. Open the layer control before and after pressing a button: it holds only the layers that match, because the others are absent rather than unchecked.

MapML-MapLibre

The attribute is observed, so a preference expressed after load is honoured the same way as one expressed before it.

This dataset is published in CBMTILE, which MapLibre cannot render; it warns and falls back to Web Mercator, so this column shows the gating working but the geometry in the wrong projection.

MapML-OpenLayers

A non-matching layer reports no label at all here, which is the clearest evidence available that its document was never requested.

This is the case the media attribute was made for. Four of the five layers are remote MapML documents; expressing a preference decides which of them the browser ever asks for, before anything is parsed and without a handler having to run. The script version fetches all five and then hides four.

Tables is the exception, and it is why this page still carries a script: a table is not map content, so there is no map element to put the query on. The handler replaces the map with the year's description table — one preference out of four that the attribute cannot express at all.

A preference change is not a map movement and has no change event of its own yet, so the page nudges the map to re-evaluate. That is a gap in the model, not in the implementations.
